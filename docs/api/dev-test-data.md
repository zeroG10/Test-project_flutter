# Рецепт підготовки даних — ПЕРЕВІРЕНО НАЖИВО 2026-09-22

Усі виклики виконані проти DEV і підтверджені відповідями сервера.

## Робочий варіант — один виклик

```http
POST /job
{
  "title":      "QA-AUTO <сценарій> <мітка>",
  "jobId":      "QA-AUTO-<унікальна мітка>",
  "userId":     "<user.id техніка>",          ← прив'язує одразу
  "surveyId":   "<published survey>",
  "statusType": "new",
  "startAt":    "<ISO-8601 Z>",
  "scheduleDate":"<ISO-8601 Z>"
}
→ 201, джоба одразу видима технікові зі статусом new
```

Прибирання: `DELETE /job/{id}` → `200`, повторний `GET` → `404`. **Перевірено.**

Обов'язкові поля — лише `title` і `jobId`; решта опційна, але `userId` і `surveyId`
потрібні, щоб джоба була осмисленою для тесту.

## ⚠️ `POST /job/assign/{phone}` джобу НЕ прив'язує

Попри назву, цей ендпоінт **не призначає конкретну джобу** — тіла запиту він не приймає.
Перевірено: після виклику `userId` лишився порожнім.

Насправді він генерує разове посилання й повертає його:

```json
{"success": true, "message": "https://copsfieldservices.dev.concerttech.com/redirect/<код>"}
```

Це флоу CR-1 із SRS §3.4.1 — SMS-посилання на джобу, дійсне 72 години, яке в мобільній
апці погашається через `POST /jobs/redeem-code`. Корисно, коли перевірятимемо сам сценарій
входу за посиланням, але **для підготовки даних не годиться**.

## Квірк читання

У відповіді `GET /job/{id}` поле `userId` повертається `null`, навіть коли джоба прив'язана.
Фактичний власник лежить у вкладеному об'єкті **`user.id`**. Перевіряти прив'язку треба саме там.

## Вибір опитування під сценарій

- звичайний потік → будь-яке `published` без префікса `Repeatable`
- **CR-2, повторювані секції** → `published` з префіксом `Repeatable` (їх 7)
- фото всередині → `Photo Upload Test Survey`
- навантаження / довгий список → `Repeatable MO12 ... Large / stress survey`
