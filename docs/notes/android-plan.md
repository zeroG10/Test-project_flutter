## 3. Структура: де що лежить

Спільне для апки лишається на місці. Усе, що стосується однієї платформи, — у підпапці `ios/` або `android/`.

```
qa/mobile/
├── README.md                    ← таблиця: модулі × iOS / Android (посилання на обидві матриці)
├── ios/                         ← final-traceability.md, not-automated.md  (перенести з …-ios.md у корені)
├── android/                     ← final-traceability.md, not-automated.md
└── <NN-модуль>/
    ├── …-checklist.md, …-test-cases.md, …-automation-plan.md, …-questions.md   ← спільне (історія рішень iOS тут)
    ├── ios/       …-traceability.md                      ← перенести з кореня модуля
    ├── android/   …-traceability.md, …-questions.md (Android D/Q), …-test-cases.md (лише Android: офлайн)
    └── bugs/      BUG-….md — один звіт на дефект, у ньому «Платформи: iOS ✓/✗ · Android ✓/✗/не перевірено»
                   evidence/BUG-…/ios/ і /android/          ← докази окремо (iOS-файли перенести, посилання оновити)

automation/mobile/
├── screens/<екран>_map.py       ← одна карта на екран, дві колонки ios= / android= (iOS-рядки НЕ чіпати)
│   └── android/                 ← екрани лише Android: системні дозволи, Chrome Custom Tabs, налаштування Android
├── pages/android/               ← поведінка лише Android
├── helpers/android/             ← adb: мережа on/off, дзвінок (intent), дозволи
├── tests/shared/                ← 124 тести, обидві платформи
├── tests/android/               ← тести лише Android (офлайн тощо)
├── builds/android/              ← APK (gitignored) + BUILD_INFO.txt
├── results/ios/<прогін>/        ← перенести сюди allure-results-* (gitignored); оновити reports/build-public.sh
├── results/android/<прогін>/
└── reports/ios/, reports/android/, reports/combined/   (gitignored)
```

**Правила:**
- **Спільне не копіювати.** Дві копії тестів чи карт — це дві правди: виправлення в одній не дійде до іншої.
- **Баг — один звіт на дефект**, бо код і бекенд спільні.
  - Якщо iOS-баг повторюється на Android — дописати у той самий звіт.
  - Баг лише на Android — новий номер із позначкою платформи.
  - Заводити — лише зі слова власника (`prompts/08`).
- **iOS-код не переносити**: його доведено трьома стабільними прогонами.
- **Скрипт прогону `automation/mobile/scripts/run.sh <ios|android> <назва>`:**
  - пише в `results/<платформа>/<дата>-<назва>/`;
  - відмовляється, якщо папка вже є;
  - стандартний `--alluredir=allure-results` + `--clean-alluredir` у `pyproject.toml` перевести на
    `results/_scratch`, щоб випадковий прогін без скрипта нічого цінного не стер.
- **Захист iOS:**
  - офлайн-тест у `unit_tests`, який падає, якщо змінився хоч один iOS-локатор (знімок iOS-колонки);
  - наприкінці — один повний прогін iOS на фінальному коді: має знову дати 115 / 5 / 4, лише тоді — звіт.
- **Після перенесень оновити шляхи:**
  - посилання в README / handoff;
  - `build_summary.py` (`DEFAULT_REASONS`);
  - `reports/build-public.sh`;
  - посилання на evidence у звітах багів.

## 5. Android-особливості інструментарію (крок 3)

- **Очищення даних** — `mobile: clearApp` (= `pm clear`) скидає й дозволи. Далі на Android 13+ з'являється
  системний запит на сповіщення — обробити, як `_first_launch` на iOS.
- **Кнопка «Назад»:** є системна кнопка й жест «назад» (з targetSdk 36 — predictive back). Звірити з тестами, які
  на iOS ходили кнопкою «Back» апки.
- **Системні дозволи** — окремі екрани в `screens/android/`: локація (дозволити / відмовити), камера й фото,
  сповіщення.
- **Вбудований браузер** — Chrome Custom Tabs, а не SFSafariViewController: інша кнопка Close та інша ознака
  завантаження (`pages/in_app_browser_page.py` має iOS-логіку).
- **Банер сповіщень** (модуль 11) вмикається через налаштування Android, а не iOS Settings.
- **Піксельні перевірки** перекалібрувати: червона крапка непрочитаного (`#EB0101`), яскравість теми (iOS: світла
  ~246, темна ~39), колір сплешу. Системні панелі Android інші.
- **Вибір фото** — системний photo picker Android; клавіатура й поле у фокусі поводяться інакше.
- **Дерево доступності Flutter на Android:** тексти здебільшого в `content-desc`, частина — в `text`. Порядок і
  позаекранні елементи перевірити на recon; на iOS були пастки, описані в handoff §7.3.
- **Мережа для офлайн-тестів** — через `adb` (напр. `svc wifi` / `svc data` або режим польоту), з обов'язковим
  поверненням мережі у `finally`.
- **Дзвінок PF** — перевіряти intent / відкриття дзвінилки; дзвінків не робити.

## 6. Повільний DEV-сервер — як зважати

- **Час очікувань** брати з замірів на recon Android, а не навмання. Наявні ліміти (напр. `LANDING_TIMEOUT` 30 с,
  збереження 20 с) — точка відліку. Підвищувати лише з доказом (заміряний час відповіді).
- **Жодних повторів тесту «до зеленого»** (правило проєкту). Якщо тест упав через таймаут:
  - спершу перевірити, чи це DEV: час відповіді API, логи апки;
  - якщо причина в середовищі — Blocked із причиною;
  - багом апки таймаут стає лише тоді, коли відтворюється на нормальній швидкості.
- **Прогони лише по одному**, ніколи паралельно з iOS: спільний тестовий акаунт і ліміт DEV на коди входу. Про
  ліміт: `ui_login` уже чекає «Too many requests … in m:ss».
- **Повний прогін Android** очікувано ~1,5–2 год.
  - Запускати у фоні з моніторингом.
  - Поки він іде — субагенти готують наступний крок (§7).
- **API-хелпери:** якщо з'являються 5xx чи обриви, записувати факти (час, запит, код) — це дані для ПМ / бекенду,
  а не привід змінювати очікування.

## 7. Моделі й субагенти (дозвіл власника 2026-09-29)

- **Основна сесія — Opus 5.5.** Субагентів можна запускати без окремого питання — щоб пришвидшити.
- **Fable 5.1** — сам, де справді потрібно, субагентом, основну сесію не перемикати. Три випадки:
  1. падіння, яке Opus не розібрав за 2 спроби;
  2. неочевидна проблема Flutter на Android: таймінги, дерево доступності;
  3. фінальне критичне рев'ю тестів і звіту перед показом.
- **Щоразу коротко повідомляти:** модель, для чого, скільки субагентів.

| Крок | Хто |
|---|---|
| 0, 1, 2 | Opus (послідовно, рішення й налагодження) |
| 3а — Android-колонка в картах | Sonnet 5, 2–3 субагенти паралельно за групами модулів (різні файли); Opus перевіряє + map-health |
| 3б — Android-інструментарій (§5) | Opus |
| 4 — прогони | модель не потрібна; зведення результатів — Haiku 4.5; рішення «баг чи тест» і виправлення — Opus |
| 5 — тест-кейси й код офлайн-тестів | Sonnet 5 (по модулю на субагента), Opus перевіряє, власник валідує тест-кейси |
| 6 — фінальні прогони | скрипти + Haiku на зведення |
| 7 — генератор звіту, рев'ю тестів | Opus; фінальне рев'ю перед показом — Fable 5.1 |

**Межі:**
- прогони йдуть по одному;
- субагенти не правлять ті самі файли одночасно; код — у своїй копії репо (`isolation: "worktree"`);
- кожен результат субагента перевіряє Opus разом з автоперевірками.

**Найбільший виграш — конвеєр:** поки йде прогін модуля, субагенти готують карти й тест-кейси наступного.

## 8. Правила, що діють далі (з iOS)

- Кожен крок — лише за командою власника: збірки, емулятор, прогони, записи в API, пуш. Субагенти й Fable — без
  окремого дозволу.
- Коміт перед кожним прогоном. Пуш — за командою.
- Репо апки — лише читання.
- **Персональні дані:**
  - дані тестового акаунта в публічних копіях приховувати (`--public`, зони маскування);
  - логи апки містять токен — не комітити;
  - з API-знімків прибирати списки адмінів / користувачів і джоб.
- Правила QA-доктрини з `CLAUDE.md`:
  - не підробляти Passed;
  - Blocked ≠ зелений;
  - виправляти тест, а не очікування;
  - баги — лише зі слова власника.
- Після кожного кроку — оновити «Статус плану» в handoff, пам'ять і `decisions.md`.
