## 1. Що за проект

- **Мета власника:** показати технічним людям і ПМ, що він уміє автоматизувати UI/E2E мобільного
  Flutter-застосунку за допомогою AI. Фінал — регресійний прогін усієї апки + переконливий звіт.
- **Продукт:** Concert Technologies Field Services — застосунок для польових техніків (роль у мобілці
  одна — Field Technician). У проді, прийнятий замовником.
- **Обсяг, погоджений з власником:** покриття вшир — усі екрани, усі переходи, наскрізний happy flow,
  ключові валідації; ~55–65 тестів; iOS спершу, потім Android. Надмірних тестів не робити.
- **Власник:** mykola.zhuchenko — останній валідатор. Пише українською, просить «людською мовою».

## 2. Правила роботи (обов'язково)

1. **Кожен крок — лише після явної команди власника.** Нічого не запускати самостійно: збірки,
   симулятори, прогони тестів, записи в API, git commit/push. Власник між кроками вносить уточнення.
2. **Модель оракула — прийнятий продакшн-базис:** апка правильна за замовчуванням; SRS/PRD/чекліст/
   дизайн пояснюють; розбіжність → питання в `<модуль>-questions.md`, не баг; критичне → власнику.
3. **Моделі:** основна сесія — Opus 5.5; масова генерація — субагенти Sonnet 5; механічне — Haiku 4.5;
   Fable 5.1 — лише за тригерами (застряг на падінні 2 рази; фінальне рев'ю перед демо). Субагенти —
   з погодження власника.
4. QA-доктрина з `CLAUDE.md`: не підробляти Passed, `Blocked ≠ green`, апка й клієнтський репо — лише
   читання.

## 3а. Що зроблено на кроці 4b і що перевірити на першому живому прогоні

Деталі — `automation/mobile/README.md` (розділи Session model, Evidence, Allure report, Summary page).

- **Нові файли:** `helpers/app.py` (запуск / перезапуск / очищення даних / перевстановлення),
  `helpers/evidence.py` (іменовані скріншоти, відео), `helpers/reporting.py` (модулі, контекст прогону, категорії
  Allure), `helpers/field_services_api.py` (прибирання тестових користувачів), `fixtures/app_state.py` (фікстури),
  `fixtures/test_data.py` (генератори `{{tech.*}}`, `{{new_user.*}}`, `{{unregistered.*}}`), `unit_tests/`,
  `automation/tools/build_summary.py` (+ тест). Заповнено `docs/environments.md` → *Test data and seeding*.
- **Знахідка з коду апки:** на iOS апка сама стирає токени з keychain при «першому запуску»
  (`TokenStorage.clearIosKeychainTokensOnFreshInstall`) → очищення даних (`mobile: clearApp`) = вихід з акаунта без
  перевстановлення. Фікстура все одно перевіряє Welcome і за потреби перевстановлює.
- **Рішення, ухвалені мною без питання (власнику — підтвердити або відкотити):**
  1. одна сесія Appium на прогін замість нової на кожен тест;
  2. нездійсненна передумова (немає `.env`, API недоступний, апка не дійшла до Welcome, UI-логін як передумова) —
     `Blocked` (skip з причиною), а не Failed; збій створення сесії Appium — як у шаблоні, fail з «Blocked:»;
  3. відео пишеться для кожного тесту, зберігається для впалих / Blocked / `e2e` (`EVIDENCE_VIDEO=auto`);
  4. новий маркер `tc("TC-…")` (один на тест) + `e2e`; conftest сам дописує Allure-тег CHK, якщо тест забув;
  5. мова зведеної сторінки — англійська (як тест-кейси); ручна оцінка часу — лише якщо власник дасть
     `--manual-minutes-per-check` (без цифри сторінка пише «not recorded»).
- **Перевірити на першому живому прогоні (крок 6):** чи `clearApp` на iOS дає Welcome без перевстановлення (у кроках
  Allure видно, який шлях спрацював); чи пишеться відео (ffmpeg + MJPEG WDA); чи прикріплюються скріншоти при
  Blocked-налаштуванні; чи сервер не обмежує часті OTP-запити на один акаунт (TC-005/006/008/009 підряд).
- **Кроку 5 треба:** сторінки з методами, на які спираються фікстури — `WelcomePage.open_login()`,
  `LoginPage.request_code(identifier)`, `OtpPage.enter_code(code)`, якорі `WelcomePage` / `JobsListPage`
  (файли `pages/welcome_page.py`, `login_page.py`, `otp_page.py`, `jobs_list_page.py`). Шаблонні заглушки
  `screens/login_map.py`, `pages/login_page.py`, `tests/shared/test_smoke_example.py` (вигадані id) — замінити/прибрати.
- **Android (крок 7):** `pm clear` скидає й дозволи → після очищення даних з'явиться системний запит сповіщень
  (Android 13+) — додати обробку тоді.

## 3в. Recon 3d — підсумок (деталі: recon-документ, «Прохід 3d»)

- **Харнес наживо працює:** сесія 9 с; `clearApp` → Welcome за 7–8 с без перевстановлення; відео пишеться (H.264);
  українська розкладка не заважає; свайп «назад» від краю працює.
- **Виправлено в харнесі за знахідками:** телефон із маскою вводиться по одній цифрі; прокрутка — короткі
  перетягування без інерції біля лівого краю, в обидва боки; дотик до поля перед введенням (+1 повтор, якщо не
  потрапив жоден символ, — крок у звіті); безіменні кнопки — предикат `name == nil` (не `''`); помилки сервера —
  пошук за текстом без типу (банер — `Other`); якір Registration — контейнер екрана.
- 🔴 **`Incorrect code.` дерево звітує видимим, хоча його не намальовано** → оракул для TC-AUTH-008 — **пікселі**
  (`helpers/pixels.py`, `BasePage.expect_drawn`; Pillow додано в залежності). Калібровано: 0.000 проти 0.10–0.15.
  Знахідка для звіту: пастка хибного Passed глибша, ніж думали в 3b.
- **Нові питання:** D-12 (на Login немає жодного повідомлення про невалідний формат — чекліст чекає «Format is
  incorrect.»), D-13 (`a b@c.com` вмикає Continue). Обидва **відкриті** — `authentication-questions.md`.
- Підтверджено дослівно: банер «This email is not registered yet…», банер «An account with this phone number already
  exists…», усі тексти OTP. Не перевірено: повідомлення для незареєстрованого **телефону** (формулювання з чекліста).
- Скріншоти й відео recon — лише локально (скретчпад сесії), у репо — тільки XML-дерева.

## 7. Контекст із розмови, якого немає в інших файлах

### 7.1 Стратегія демо і звіту (погоджено з власником)

- **Аудиторія демо:** технічні люди + ПМ. Звіт — два рівні в одному документі: зверху півсторінки
  для ПМ (скільки покрито, скільки часу економить проти ручної регресії, які ризики знайдено), нижче
  технічна частина (матриця трасування, Allure, контекст прогону, що свідомо не автоматизовано і чому).
- **Що переконує (не «100% зелене» — воно насторожує):** доведений червоний для кожного тесту;
  трасування `FR-xxx → CHK → TC → тест → вердикт` (у SRS 154 вимоги з кодами); чесні `Blocked`
  з причиною; контекст прогону (білд, пристрій, ОС, дата); повторюваність — 3 стабільні прогони
  поспіль (історія Allure); знахідки процесу (CR-2 без покриття в чеклісті, 31 перевірка без статусу,
  темна тема — 3 перевірки на весь застосунок, розбіжності D-1…D-5, захист локації, пастка хибного
  Passed на OTP); цифра для ПМ — час ручної регресії 625 перевірок × конфігурації проти автопрогону.
- **Цифри скоупу:** 625 перевірок; breadth-suite закриває ~284 унікальні (45%): переходи 111,
  «елемент відображається» 128, успішні сценарії 113. Груба класифікація всього чеклісту: навігація
  і дії 237, валідація 105, стан/дані 40, візуал 45, інше 198.
- **Архітектура набору (4 рівні):** досяжність кожного екрана (~15–18) → переходи між екранами +
  назад (~20–25) → наскрізний happy flow логін→список→джоба→check-in→опитування→фотозвіт→нотатка→
  здача→check-out (3–5 довгих) → ключові валідації (~10). Разом 55–65. Тести з маркером `shared`
  ганяються на обох платформах без переписування.
- **Політика доказів:** скріншот + page source на падінні — вже вшито в `conftest.py`; іменовані
  скріншоти на ключових моментах happy flow і відеозапис наскрізного сценарію — **ще треба додати**
  в харнес перед написанням тестів. Не знімати все підряд.
- **Логін:** один раз на прогін, далі тести в відкритій сесії (`noReset`) — через FR-OTP-13
  (блок акаунта на 2 хв після надлишку спроб) і таймер повторної відправки. Перевірки самого входу —
  окремий набір із чистого стану. Альтернатива для тестів, яким логін не цікавий: токен через API
  (`POST /auth/sign-in/phone|email` + OTP) — не перевірено, чи можна підкласти токен у апку.
- **Скоуп-рішення:** планшети поза демо; темна тема — лише перемикач (3 перевірки); 31 перевірка без
  статусу — Skipped; система COPS (онбординг, SMS-згода FR-001…007) — поза межами; мінімальні ОС —
  не проганяємо. Усе з причинами в `decisions.md`.
- **Нові перевірки CR-2** пишуться з PRD і приносяться власнику на валідацію до автоматизації:
  додати екземпляр (Add Room), редагувати без дубля, видалити з підтвердженням, автонумерація без
  ручного перейменування, незаповнений екземпляр блокує відправку, чернетка/офлайн, фото прив'язані
  до екземпляра. На DEV є 7 опублікованих опитувань з префіксом `Repeatable` (`docs/api/dev-test-data.md`).
  На картках секцій у коді є `ValueKey('section-card-…')`, але нативні драйвери їх не бачать.

### 7.5 Погоджений план модулів після пілота (з розмови 2026-09-23 — у файлах більше ніде)

**Бажання власника:** бізнес-логіка важлива; **опитування — серце джоби**, «розширити перевірки для різних
видів опитувань — не занадто, але достатньо, щоб у звіті було видно, що там усе ок». Джоба складається з
опитування, фотозвіту й нотаток — усе це покрити. Апка пройшла прийомку, але «це не значить, що багів не
може бути» — шукати їх цілеспрямовано там, де ризик найвищий (CR-2, негативні шляхи, збереження стану).

**Опитування (08) — дерево класифікації, 8 репрезентативних опитувань DEV** (id — `docs/api/dev-test-data.md`):

| Опитування | Що доводить |
|---|---|
| Mo3 All Question Types | кожен тип поля: ввід, відображення, збереження |
| Fiber Site Survey | реалістичне наскрізне: число (єдине опитування з ним), 3 повторювані секції, логіка, `__end__` |
| End Survey | дострокове завершення: після «кінцевої» відповіді решта ховається, опитування зберігається |
| Mo5 Radio Logic Mapping | розгалуження: кожен варіант веде у свою гілку (таблиця рішень) |
| T8 Branching Workflow | переходи між секціями |
| Repeatable TWO sections with logic+questions | CR-2 + логіка всередині екземпляра секції (найскладніший випадок рушія) |
| Repeatable Single section without logic | CR-2 база: додати / редагувати / видалити / автонумерація |
| Short Survey | найпростіший випадок |

Плюс Photo Upload Test Survey (фото в опитуванні) і **одне порожнє опитування** (0 питань) — має коректно
працювати. «21 повторювана секція» — прибрано (щадний режим DEV).

**Що перевіряємо в опитуваннях:** кожен тип поля (текст — межі 500/501, FR-SUR-02); обов'язковість, Save
вимкнена до заповнення, помилка біля питання (FR-SUR-03/04/05); **логіка переходів** — видно рівно потрібні
питання; **зміна відповіді після переходу** (гілка А → Б: питання А зникають) — тут рушії ламаються найчастіше;
`__end__` і переходи між секціями; автозбереження й перезапуск (FR-SUR-06/07/11-1); Save → «завершене» →
повернення до джоби (FR-SUR-11); **що дійшло на сервер** — звірка відповідей через API, для повторюваних
секцій — вкладена структура PRD §9.3; CR-2: Add Room → «Room 1, 2…», редагування без дубля, видалення з
підтвердженням, незаповнений екземпляр блокує відправку з повідомленням про нього, фото прив'язані до
екземпляра (PRD stories 3–6, §9.2, §14.2). Значення `options.enabled` на питанні — з'ясувати на живій апці.

**Еталони логіки — явні таблиці рішень у тест-кейсах, НЕ другий рушій у тестах.** Вручну розібрати
визначення кожного з 8 опитувань (`GET /survey/{id}`, логіка на `answers[].logic`) і виписати: «обрали X →
видно Q3, Q5, Q7; Q4, Q6 сховані». Власник валідує таблиці — вони стають еталоном. Причина: переписаний у
тести рушій відтворив би ті самі помилки.

**Розкладка «робочої частини» джоби (~40 кейсів):** опитування ~16, CR-2 ~8, фотозвіт ~6, нотатки ~5, здача ~5.
- **Фотозвіт (09):** додати з галереї; кілька фото; опис і теги; редагувати опис; видалити з
  підтвердженням; збереження після перезапуску. Фоторедактор (розмітка/обрізка) — частково, решта `Blocked`
  (кнопки без імен, полотна й палітри нема в дереві). **Камера на iOS-симуляторі недоступна — лише галерея**
  (`xcrun simctl addmedia`, фото `automation/mobile/fixtures/media/site_photo.jpg`).
- **Нотатки (10):** додати, редагувати, видалити з підтвердженням; порожня не зберігається; збереження після
  перезапуску.
- **Здача (07):** без обов'язкових частин не здати; успіх — «Deliverables sent to review successfully»; після
  здачі редагувати не можна; статус джоби на сервері змінився.
- **Офлайн опитувань (FR-SUR-12/13)** — на iOS-симуляторі мережею не керувати; **додати на етапі Android**.

**Статуси джоб (03–07) — переходи станів, два блоки:** (1) відображення — створити через API джоби одразу в
кожному статусі (`new`, `in_progress`, `submitted`, `completed`, `canceled`, `expired`) і перевірити бейдж,
фільтр, календар (лише New / In Progress), доступні дії (Check in лише для New тощо); (2) переходи — технік:
New → check-in → In progress → здача → Submitted → далі; менеджер: скасувати / протермінувати через API, поки
апка відкрита. У чеклісті ~40 пунктів про статуси. **Спостереження:** чекліст згадує кнопки-фільтри New / In
Progress / Completed на списку джоб — на живому екрані їх не було; порожній стан в апці «No jobs», у чеклісті
«No orders» — перевірити в модулі 03.

**Звітність:** зведену сторінку для ліда (скріншоти інтерфейсу замовника) **публікувати лише за командою
власника**. Allure — по модулях, скріншоти в ключових точках і на падінні, відео наскрізних і впалих тестів.

**Глибина:** пілот Auth — вузький (14 кейсів / 82 пункти). Для решти модулів глибину вирішуємо після пілота.
Довідка для розмови про глибину: ручний розбір 126 пунктів Auth показав ~78% автоматизується прямо, ~15% з
додатковими зусиллями, ~7% ні — тобто повна глибина по апці ≈ 80–85% чеклісту, ~150–180 кейсів, ~3–4 тижні.
